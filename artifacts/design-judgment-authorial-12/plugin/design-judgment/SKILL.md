# Design Judgment Authorial 12

Preserve native model bandwidth. Add one bounded judgment stage only when it changes a consequential decision.

## Route by the actual state of the work

- **Direction is materially open:** use `design-direct` before implementation.
- **An authoritative visual world already exists:** inherit it; do not reopen direction.
- **A stable artifact exists but needs judgment:** use `design-edit` in a fresh context.
- **Structure is accepted and only felt craft remains:** use `design-finish` in a fresh context.
- **A successful world must persist across surfaces:** use `design-systematize` after verification.
- **A known artifact type has a proven specialist:** the builder may receive exactly one specialist.
- **Native judgment is already sufficient:** use no Design Judgment body.

## Context boundary

The parent owns registry retrieval, condition identity, rendering, objective evidence, repair authorization, and delivery. A stage receives only its task packet and zero to three compact evidence payloads. The builder receives the compact brief, one selected world card, one truth spine, fixtures, and at most one specialist.

Never stack stage skills in one context. Never send discarded directions, reviewer rubrics, registry administration, or experiment-control prose to the builder.

## Authority

Product truth and user decisions outrank this plugin. A practitioner heuristic cannot override normative evidence, platform authority, an established design system, or a valid contextual exception. Mechanical proof establishes the floor; it does not choose the direction.
