# Repository legibility for coding agents

An agent-ready repository makes architecture, conventions, validation, and ownership discoverable from the files. The objective is not documentation volume; it is low-ambiguity decision support.

## Minimum legibility surface

1. **Root map:** purpose, major packages/services, dependency direction, entry points, generated files, and fast commands.
2. **Layered AGENTS.md:** global invariants at root; narrower overrides near specialized code; no duplicated or contradictory guidance.
3. **Executable validation:** one fast command for formatting/static checks/unit tests and one full release command.
4. **Architecture records:** current decisions, constraints, consequences, and supersession status.
5. **Representative examples:** canonical implementations and tests, not only prose conventions.
6. **Ownership and boundaries:** public APIs, state owners, effect boundaries, data classifications, and areas requiring approval.
7. **Artifact truth:** generated outputs, migrations, schemas, fixtures, screenshots, and manifests live where reviewers can inspect them.

## Repository map template

```markdown
# Repository map
- `crates/domain`: provider-independent state, policies and effects
- `crates/runtime`: Tokio supervision, queues, cancellation
- `crates/adapters`: model/tool/protocol implementations
- `crates/app`: composition root and configuration
- `tests/scenarios`: end-to-end agent/effect fixtures

Dependency rule: domain <- application <- adapters/runtime <- app.
Fast check: `...`
Full check: `...`
Do not edit: `...` (generated by ...)
```

## Decision locality

Put guidance at the narrowest scope that owns it. A repository-wide security invariant belongs at root. A crate-specific error convention belongs beside that crate. A one-off migration plan belongs in the task plan, not permanent instructions.

## Promote corrections deliberately

- preference or convention → AGENTS.md;
- reusable judgment workflow → skill;
- deterministic transformation/check → script/linter;
- correctness invariant → test/type/schema;
- architectural tradeoff → ADR;
- recurring agent failure → eval fixture;
- privileged action → harness policy/approval.

## Quality tests

A fresh coding agent should be able to answer, from the repository alone:

- What does this system do and where does a change belong?
- Which files are authoritative or generated?
- What must not change?
- How is the smallest useful validation run?
- What evidence is required before completion?
- Where are security, data, and effect boundaries?
- Which decisions require human approval?

When it cannot, fix repository legibility before adding more conversational context.
