## 1. How to use this file

Read this file when:

- changing a skill’s routing or procedure;
- changing evaluation, release, protocol, observability, security, lifecycle, or field-learning policy;
- deciding whether an older research requirement is still current;
- expanding an external protocol or effect boundary; or
- making a claim that depends on current external guidance.

Do not load it for every ordinary skill invocation. A stage or implementer should receive only the relevant foundation rows and repository evidence.

The categories are:

- **Controlling current:** current official versioned specification or product guidance directly applicable to implementation.
- **Stable supporting:** strong principle that still requires local design judgment.
- **Empirical directional:** paper/benchmark that defines a hypothesis; local held-out evaluation remains required.
- **Draft provisional:** official draft or concept paper; cannot establish final conformance.
- **Emerging, not normative:** initiative/roadmap/webinar/research direction.
- **Historical lineage:** preserved for provenance, not current execution or release authority.

## 2. Current foundational decisions

### A. Prompts, skills and active context

1. **Use lean, nonrepetitive standing instructions.**
   Source: OpenAI GPT-5.6 Model Guidance — https://developers.openai.com/api/docs/guides/latest-model
   Status: controlling current.
   Decision: state each standing rule once; expose relevant tools only; remove one group at a time and rerun representative tasks. Do not use generic “think deeply” or compare-many-approaches language as permanent policy.

2. **Keep high-signal skill procedure; move nonactionable material on demand.**
   Sources: SkillReducer — https://arxiv.org/abs/2603.29919; SkillRouter — https://arxiv.org/abs/2603.22455.
   Status: empirical directional.
   Decision: move examples, schemas, background, generic catalogs and version history out of default bodies, but preserve body-resident routing and procedural signal. Every reduction requires body-aware activation and final-state evaluation.

3. **Select zero to few skills adaptively.**
   Source: SkillsInjector — https://arxiv.org/abs/2605.29794.
   Status: empirical directional.
   Decision: no-skill is valid; one-decision tasks must not stack several advisers. Skill count is not capability.

4. **Do not assume repository context improves correctness.**
   Sources: https://arxiv.org/abs/2602.11988 and https://arxiv.org/abs/2607.27250.
   Status: empirical directional.
   Decision: evaluate the current and reduced packages against no-skill/native baselines. Context reduction is a cost and attention hypothesis, not a correctness claim.

5. **Use parent-owned bounded retrieval.**
   Source: Design Judgment Authorial 11/11.1 technical package, 2026-08-08.
   Status: project empirical directional.
   Decision: deep evidence can remain outside creator context; the parent selects zero to three compact relevant payloads. Do not add a new registry engine unless the existing profiles and references fail measured routing/selection requirements.

### B. Architecture and orchestration

6. **Use the smallest architecture that resolves the current uncertainty.**
   Sources: OpenAI Harness Engineering — https://openai.com/index/harness-engineering/; Anthropic Building Effective Agents — https://www.anthropic.com/engineering/building-effective-agents; Prompt-Induced Waste — https://arxiv.org/abs/2608.01347.
   Status: stable supporting plus empirical directional.
   Decision: direct call/workflow before loop; loop before graph; graph/durability/multi-agent only for named state, recovery, branching, or interoperability requirements.

7. **Multi-agent use must preserve expertise and independent ownership.**
   Source: Multi-Agent Teams Hold Experts Back — https://arxiv.org/abs/2602.01011.
   Status: empirical directional.
   Decision: use a root integrator and only genuinely independent specialist work. Do not use committee consensus, universal reviewer teams, or agent count as quality evidence.

8. **One implicit effectful front door remains an architecture decision, not a research law.**
   Repository decision: UltraGoal is the external implicit gateway; Agentic specialists are explicit and proposal-only.
   Decision: preserve until clean-host and behavioral evidence contradicts it. No source alone can grant Agentic advisers effect or claim authority.

### C. Verification and evaluation

9. **Grade the actual requested product boundary.**
   Source: Building to the Test — https://arxiv.org/abs/2606.28430.
   Status: empirical directional.
   Decision: required and prohibited final-state outcomes on the exact candidate are primary. Test counts, routing traces, receipts and reviewer narratives are supporting evidence.

10. **Separate activation, isolated value, composition, host, and field claims.**
    Sources: OpenAI skill eval guidance; Design Judgment Authorial staged evaluation.
    Status: current design decision.
    Decision: a good route does not prove useful advice; a good isolated adviser does not prove composition; structural package integrity does not prove field value.

11. **Use evaluator-owned capture and equivalent-output resolution.**
    Source: Design Judgment v5 collector correction.
    Status: direct project evidence.
    Decision: producer conditions must not be penalized for filenames, evidence paths, or browser access that belong to the evaluator. Completed poor output is scored, not content-retried.

12. **Treat model reviewers as fallible.**
    Sources: https://arxiv.org/abs/2603.05485 and current code-review judge studies.
    Status: empirical directional.
    Decision: use deterministic endpoints where possible, blind randomized review, position-swapped sentinels, explicit ties/insufficient evidence, and counterfactual validation of material findings.

13. **Long written policies do not enforce consequential behavior.**
    Source: HANDBOOK.md benchmark — https://arxiv.org/abs/2607.25398.
    Status: empirical directional.
    Decision: authority, package identity, irreversible effects and release gates remain code-/permission-/schema-enforced.

### D. Human control and product outcomes

14. **Human authority requires informed decision support.**
    Source: Amershi et al., Guidelines for Human-AI Interaction — https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/.
    Status: stable supporting, peer-reviewed.
    Decision: disclose capability and limits, support correction/dismissal, scope uncertainty, show decision-relevant reasons and consequences, and preserve user controls.

15. **Optimize for appropriate reliance, not trust or approval rate.**
    Source: Microsoft Appropriate Reliance initiative — https://www.microsoft.com/en-us/research/articles/appropriate-reliance-research-initiative/.
    Status: empirical directional.
    Decision: show evidence, uncertainty, alternatives and contradictions. Explanations alone do not prove correctness and can increase confidence in wrong output.

16. **AI assists a delivery system; it does not replace product direction.**
    Sources: DORA 2025 report — https://dora.dev/research/2025/dora-report/; user-centric focus — https://dora.dev/capabilities/user-centric-focus/.
    Status: stable supporting.
    Decision: evaluate product outcomes, supervisory work, rework, flow and stability rather than output volume or agent activity.

17. **Use small batches.**
    Source: DORA Working in Small Batches — https://dora.dev/capabilities/working-in-small-batches/.
    Status: stable supporting.
    Decision: change one mechanism/skill cluster per experiment. Do not rewrite the full portfolio before the four-skill slice demonstrates value.

### E. Security, protocols and supply chain

18. **SSDF 1.1 is final; SSDF 1.2 is provisional.**
    Sources: https://csrc.nist.gov/pubs/sp/800/218/final and https://csrc.nist.gov/pubs/sp/800/218/r1/ipd.
    Status: controlling current plus draft provisional.
    Decision: use SSDF 1.1 as stable secure-development guidance. Consolidate the two draft entries and label all 1.2-derived guidance provisional.

19. **SLSA 1.2 is current for provenance, not behavior.**
    Source: https://slsa.dev/spec/v1.2/.
    Status: controlling current.
    Decision: bind source/build/package identity and protected release process. Do not use SLSA provenance to claim routing, task, security completeness, or product value.

20. **MCP must be updated to the 2026-07-28 protocol era.**
    Source: https://blog.modelcontextprotocol.io/posts/2026-07-28/.
    Status: controlling current.
    Decision for new implementations: stateless-first; avoid new dependencies on deprecated Roots, Sampling, Logging, Dynamic Client Registration and legacy HTTP+SSE. Maintain compatibility only where a current consumer needs it. Use full JSON Schema 2020-12 where supported.

21. **A2A v1.0 is for independent interoperable agents, not internal workers.**
    Source: https://a2a-protocol.org/latest/announcing-1.0/.
    Status: controlling current.
    Decision: adopt only for a real cross-system interoperability requirement. Native subagent delegation and tool calls do not require A2A.

22. **NIST agent initiatives are emerging.**
    Sources: https://www.nist.gov/artificial-intelligence/ai-agent-standards-initiative and https://csrc.nist.gov/pubs/other/2026/02/05/accelerating-the-adoption-of-software-and-ai-agent/ipd.
    Status: emerging/draft, not normative.
    Decision: preserve explicit identity, authorization and auditability; do not claim conformance or create mandatory law IDs from initiative documents.

### F. Runtime, observability and field learning

23. **Keep domain evidence independent of telemetry standards.**
    Source: OpenTelemetry specs — https://opentelemetry.io/docs/specs/.
    Status: controlling current, version-sensitive.
    Decision: current versions at the lock are OTel 1.59.0 and semantic conventions 1.43.0. Map stable fields selectively; version experimental GenAI fields; do not store raw prompts/tool payloads by default.

24. **Durability requires deterministic orchestration and idempotent effects.**
    Source: Temporal official docs — https://docs.temporal.io/.
    Status: stable supporting.
    Decision: keep action/effect IDs, idempotency, reconciliation, crash/replay tests. Temporal is an optional implementation, not a universal requirement.

25. **Feature assignment is not exposure or authorization.**
    Source: OpenFeature — https://openfeature.dev/specification/.
    Status: stable supporting.
    Decision: use only for rollout/experimentation needs; record actual exposure separately; a flag never authorizes a privileged effect.

26. **NIST AI 800-4 is a challenge taxonomy.**
    Source: https://doi.org/10.6028/NIST.AI.800-4.
    Status: stable supporting.
    Decision: use its monitoring categories to formulate questions. Correct R75 and do not require a universal monitoring stack from it.

## 5. Foundation update workflow

When a source changes:

1. Identify the affected foundation ID.
2. State the exact old and new claim.
3. Identify the current repository decision and canonical owner.
4. Choose `no_change`, `update`, `replace`, or `retire`.
5. Prefer a code/test/tool change for deterministic behavior.
6. Change prose only when a noninferable semantic decision changed.
7. Add or update one held-out case when the change is behaviorally material.
8. Record one row in the foundation log only when the decision must survive the session.
9. Do not update historical source counts, every skill, or every matrix unless a real reader requires it.

## 6. Claim ceilings

| Evidence | Maximum claim |
|---|---|
| Source review | The source supports the exact stated principle. |
| Structural validators | The exact package satisfies those structural checks. |
| Activation heldout | The candidate routes/abstains on the tested prompt distribution. |
| Isolated advice experiment | The adviser changes tested builder outcomes under the frozen protocol. |
| Composition experiment | The selected advisers compose on the tested two-decision tasks. |
| Clean-host journey | Exact archives install/discover/invoke/coexist/uninstall in the tested host. |
| Field use | Observed users/tasks in the tested operating envelope experienced the reported outcomes. |

No lower row proves a higher row.

## 7. Review triggers

Review this foundation file when:

- OpenAI changes GPT-5.6/Codex skill or plugin behavior;
- MCP, A2A, OTel, SLSA, SSDF or relevant SDKs release a new current version;
- a held-out activation or final-state evaluation fails;
- one skill repeatedly overactivates or causes scope/authority defects;
- a real field observation changes the product/lifecycle decision;
- an existing source row is found to be misquoted or over-operationalized; or
- a current reader of a historical research artifact is removed.

Age alone does not invalidate a stable principle. Version-sensitive implementation guidance must be rechecked at use.
